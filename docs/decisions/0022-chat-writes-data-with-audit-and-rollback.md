# 0022. The chat can write data, scoped to cells and rows, confirmed before it commits, with audit logging and rollback as the actual safety net

**Status:** accepted, implemented. `propose_write_query`/`confirm_write` existed at the database level since this ADR was first accepted, but were never actually wired into `chat`'s tool loop or any UI -- discovered while implementing [0023](0023-producer-memory-via-embeddings.md), confirmed by grep, not assumed. Two things closed that gap: `chat` now has a `propose_write_query` tool (never `confirm_write` -- that stays a real click, never the model's own judgment, exactly as designed below), and the generic `audit_row_change` trigger -- which existed as a function but was attached to zero tables -- is now attached to every table with a real write grant to `authenticated`, including `parcel_shares` via its own dedicated trigger function (see Consequences). A later re-audit of this ADR's own checklist found and closed one more gap, on `pending_writes` itself rather than a producer-data table (see Consequences).

## Context

`0016` made the chat's SQL tool strictly read-only, enforced by Postgres' own `transaction_read_only` mode -- deliberate, and correct for what was known then. Real use since has made a write-capable chat worth real consideration: a producer describing what they observed, or asking the chat to correct something, currently dead-ends at "I can't do that."

The explicit direction for this decision: give the chat a genuinely general write capability -- not a narrow, hand-written RPC per use case (the same "fixed menu, one resolver per shape" ceiling `0016` already hit once and rejected for reads) -- and make it safe primarily through audit logging and rollback, not through restricting what SQL the model is allowed to write. The one explicit boundary: **data, not structure** -- the chat can change what's in a cell, never create a column or a table.

Working out the actual mechanism surfaced two things worth being explicit about before this ships:

- **RLS scopes rows, not column values.** A producer's own `profiles` row is update-able by them under existing RLS -- but nothing stops a write tool from setting that row's `producer_id` to a different producer's ID, which would be an instant, silent cross-tenant privilege escalation with no bug in RLS required. This has to be closed at the column-privilege level, not assumed away by "RLS already handles it."
- **"Rollback" is not an unconditional guarantee**, and this ADR should say so rather than imply it: it reverts specific row changes cleanly when caught reasonably promptly; it does not undo a real-world action a producer already took based on wrong data, does not cleanly resolve a revert against rows that received *further, legitimate* edits after the bad write, and does not apply to anything outside DML (the boundary above already rules that out). It is the actual safety net this decision relies on, but it has real edges.

## Decision

**Writes are confirmed before they commit -- a real click, not the model's own judgment about whether it was told to proceed.** The original chat-submission flow (`0009`) confirmed with the producer before landing anything; `0016` removed that flow along with the rest of chat-based submission, but the underlying principle -- a write commits only after a real, mechanical confirmation, not because the model decided it had enough context -- is exactly the "safety lives in mechanisms, not trust" discipline `0016` itself names as this project's own standard. This decision brings that principle back in a form that fits a general write tool instead of a narrow submission form.

**Two tools, not one: `propose_write_query` and `confirm_write`.**
- `propose_write_query(query)` runs the caller's DML inside a transaction that always rolls back -- a real dry run against the real schema, under the caller's own `security invoker` session, so RLS and every real Postgres constraint (types, `NOT NULL`, `CHECK`, foreign keys) apply exactly as they would for real. It captures what the query *would* affect (via `RETURNING`), stores the query text and that summary in a new `pending_writes` row (`id`, `producer_id`, `query`, `summary`, `status` default `'pending'`, `created_at`), and returns the proposal's id plus a human-readable summary for the model to relay to the producer as an actual confirm/cancel UI affordance -- not a plain-text question the model asks and free-text "yes" answers.
- `confirm_write(proposal_id)` -- called only by the producer clicking that real UI affordance, never by the model on its own -- re-runs the same stored query for real, inside a real transaction, marks the `pending_writes` row `'applied'`, and is what the audit trigger below actually fires against.

**The dry run in `propose_write_query` is the validation step, not a separate mechanism.** A malformed value, a `NOT NULL` violation, a foreign key that doesn't resolve, a `CHECK` constraint violation -- all of these fail loudly inside the dry-run transaction before the producer is ever shown a confirmation prompt, the same way any real write would fail, just without anything actually committing. Postgres' own type system and declared constraints are doing this validation, not new code written for this decision. Where a table's real invariants aren't yet expressible as a constraint at all (a `dead_date` that has to be on or after `planted_date`, a `position` that has to fall within its row's real length) -- those get added as real `CHECK` constraints when that table is brought into the write tool's reach, the same evidence-first precedent `0019`'s `FIELD_RANGES` already set for weather data: validate against a real, named rule, not a blob that might be anything.

**Both tools share the same mechanism `execute_readonly_query` already established.** Same `security invoker` (runs as the calling producer's own session, never elevated), same statement timeout, no text-based query inspection -- safety comes from what Postgres' own privilege system and RLS actually allow the `authenticated` role to do, the identical philosophy `0016` already used for enforcing read-only.

**The data/structure boundary is enforced by a privilege that already happens to be true today, verified directly rather than assumed:** `authenticated` has `USAGE` but not `CREATE` on the `public` schema, has no `TRUNCATE` grant on any table, and owns none of them (every `public` table is owned by `postgres`). `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, and `TRUNCATE` are therefore already structurally unreachable from this role -- this ADR's job is to keep that invariant true (never grant `authenticated` schema-level `CREATE` or table ownership going forward), not to build new enforcement for it.

**Column-level privilege escalation gets a real fix, not an assumption.** Any column whose *value* controls access scope -- `profiles.producer_id` is the concrete case found while designing this -- gets `UPDATE` explicitly revoked from `authenticated` at the column level (`revoke update (producer_id) on public.profiles from authenticated`), while the rest of the table's normal columns keep whatever grants they already have. This is checked per-table as tables are brought into scope for the write tool, not assumed safe by default.

**Every committed write goes through a generic audit trigger, not a per-table one written by hand.** One trigger function, attached to each table the write tool can reach, fires on `INSERT`/`UPDATE`/`DELETE` and records the affected row's id, the table, the operation, the old row (as `jsonb`, null for `INSERT`), the new row (`jsonb`, null for `DELETE`), `auth.uid()`, the originating `pending_writes.id`, and a timestamp into a new `audit_log` table. Only `confirm_write`'s real commit ever fires this trigger -- `propose_write_query`'s dry run rolls back before any trigger's effects could persist. This is the mechanism the rest of this decision depends on -- it has to exist and be verified working before `confirm_write` is granted to anyone.

**Rollback reverts specific captured field values, not a whole-row or whole-table snapshot.** Given an `audit_log` row (or a set of them from one chat turn), reverting means writing the captured old values for the fields that changed back onto the current row -- if the row has been legitimately edited again since, only the fields the bad write actually touched get reverted, not the whole row wholesale. This is deliberately more conservative than a snapshot restore, precisely because a snapshot restore is exactly what would clobber a later legitimate edit.

**What this does not solve, named explicitly rather than implied away:**
- A producer who already acted in the real vineyard on bad data before it was caught -- reverting the row doesn't reach that.
- A bad write that goes uncaught long enough that untangling it from subsequent real edits stops being a clean, mechanical revert.
- Anything outside this project's own Postgres -- this is a database-level safety net, not a general undo button.

**Daily backups (30-day retention) are a separate, coarser safety net, not a replacement for the audit log.** The audit log is for "revert this one write we can point to"; backups are for "something went wrong in a way the audit log itself didn't anticipate." Both are named in the original request and both are real; this ADR's `audit_log` mechanism doesn't stand in for the backup/restore work, which is its own decision.

## Consequences

- The chat's write ceiling is "whatever DML it can construct against a schema it can see," the same shape `0016` already gave it for reads -- bounded by RLS, the column-level revokes named above, and the already-true absence of DDL/TRUNCATE privilege, not by a curated list of allowed operations.
- Nothing commits without a real confirmation click -- a wrong or misunderstood request costs the producer one extra look at a summary before anything changes, not a silent bad write discovered later. That's a real added step to every write, deliberately, in exchange for removing "did the model actually have enough context" as a live risk.
- `pending_writes` rows that are never confirmed (the producer declines, or just moves on) are inert leftovers -- worth a retention/cleanup pass, not decided here.
- `audit_log` is a new, likely fast-growing table -- retention/pruning for it is not decided here and should be before it ships, the same evidence-first discipline this project applies to everything else.
- A future table added to the write tool's reach needs its own pass through this ADR's checklist (attach the audit trigger, check for any access-scoping columns that need a column-level revoke, add any real `CHECK` constraints for invariants Postgres doesn't already know about) -- this is a per-table onboarding step, not automatic.
- Real risk surface is now "what DML the model can construct, and whether every table it can reach actually got the column-privilege and constraint review this ADR calls for" -- worth re-auditing any time a new table is added to what the write tool can touch, the same re-verification caveat `0016` already states for its own enforcement mechanism.
- The confirm/decline UI affordance is a fenced ```confirm-write``` code block in the model's own markdown reply, containing `propose_write_query`'s own `{proposal_id, summary}` JSON -- the frontend recognizes it (`ConfirmWriteCard.tsx`) the same way `0021` already taught it to recognize a ```svg``` block, rather than inventing a second mechanism for "the model emits something the frontend turns into a real UI element." Decline updates `pending_writes.status` to `'declined'` directly from the browser, under the same RLS as everything else -- no new RPC needed for that half.
- `parcel_shares`' own onboarding pass is done: it gets its own trigger function (`audit_parcel_share_change`), not a bent version of the generic one, since it has no `producer_id` column of its own -- audit attribution resolves the owner via a join to `parcels` instead. That join surfaced a real bug caught by scratch-testing before it shipped: deleting a parcel cascades to its shares, and by the time the trigger fires for that cascaded delete, the parent `parcels` row is already invisible to a plain `SELECT` -- the join would resolve to null and crash the `NOT NULL` constraint on `audit_log.producer_id`, breaking parcel deletion itself whenever a share existed. Fixed by skipping the audit insert when the owner can't be resolved, since a share disappearing along with its own parcel isn't independently revertible anyway.
- **`pending_writes` itself never went through this ADR's own checklist**, since it's the mechanism's staging table, not a producer-data table the model proposes writes against -- confirmed by scratch-testing (not assumed) that it was a real gap anyway: `authenticated` held a table-wide `UPDATE` grant (needed because `propose_write_query`/`confirm_write` are both `security invoker`, so their own internal writes run as the calling producer's session), but the only legitimate client-side write is `ConfirmWriteCard`'s Decline button setting `status`. A raw client update could silently rewrite a pending proposal's own `query` text after the producer had already been shown a summary of a *different* query -- `confirm_write` re-reads `query` at confirm time, not at propose time, so the two could end up disconnected, the same "grant allows more than the legitimate use needs" gap this ADR already named for `profiles.producer_id`. Closed by narrowing the grant to `update (status)` only; `INSERT` stays table-wide since RLS's own `with_check` already stops a producer inserting a proposal under someone else's `producer_id`. Deliberately did not attach the generic audit trigger here -- the real committed write already gets audited on whichever table `confirm_write`'s query actually touches, and auditing a proposal's own create/decline lifecycle would double-log without giving a revert anything new to act on.
